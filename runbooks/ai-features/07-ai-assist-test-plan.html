F

Accuracy guardrails

A confident wrong answer is worse than no answer — but a correct refusal that sounds apologetic still costs you the room. These check both: the agent must never invent, and never describe the product by what it lacks.

F1Entity that doesn't exist — must not invent
كم عدد الشكاوى المسجلة هذا العام؟

Expect

One short clause that complaints aren't among these records, then an offer to look in tasks/decisions/agenda, then one question. Shape: الشكاوى لا تُدار ضمن سجلات الحوكمة هنا…

Fails if

It invents a number; says لا توجد شكاوى (implying the feature exists and is empty); mentions its own tools (لا تتوفر لدي أداة); or recites platform scope (المنصة تركز على… / هذا النظام مخصص لـ…).

F2A detail the records don't hold
ما ميزانية لجنة المراجعة لهذا العام بالريال؟

Expect

It searches first, then declines without inventing a figure, and offers to look for a decision or minutes that mention a budget.

Fails if

It invents a riyal amount, presents a decision title as if it were the budget, or opens with a scope disclaimer instead of the offer.

F4Empty ≠ non-existent — the distinction must hold
كم اجتماعاً لدينا في يناير 2027؟

Expect

Meetings are tracked, this period is simply empty — so it reports none scheduled for that month and offers to create one.

Fails if

It answers like F1 (لا تُدار هنا) — that would tell the user meetings aren't a feature.

F5Decline tone holds across different missing entities
اعرض لي طلبات الإجازات للموظفين1 ما إجمالي رواتب الموظفين هذا الشهر؟2

Expect

Both follow the F1 shape. Neither mentions tools, capabilities, or what the platform "focuses on".

Fails if

Either one lists the platform's covered areas — that reads as a limitation to a prospect.

F3Arabic only — no bilingual leakage
اعرض حالة جميع المهام مع أصحابها وتواريخ استحقاقها

Expect

Pure Arabic. Statuses as مكتملة / قيد التنفيذ / جديدة, priorities as عالية / حرجة.

Fails if

You see IN_PROGRESS, HIGH, or English in parentheses after Arabic terms.

S

Streaming protocol

The stream carries two vocabularies at once: the original frames (so nothing regresses) and the newer AG-UI run/step/tool events. Run these from a terminal. Get a token first:

TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \ -H 'Content-Type: application/json' -H 'X-Tenant-Slug: acme' \ -d '{"identifier":"admin","password":"P@ssw0rd"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["accessToken"])')
S1Both vocabularies present, legacy frames intact
curl -sN -X POST http://localhost:8080/api/ai/assist/agent/stream \ -H "Authorization: Bearer $TOKEN" -H 'X-Tenant-Slug: acme' -H 'Content-Type: application/json' \ -d '{"query":"كم عدد المحاضر؟"}' | grep -o '"type": *"[A-Za-z_]*"' | sort | uniq -c

Expect

Legacy delta, tool, done all present, and RUN_STARTED, STEP_STARTED, TOOL_CALL_START, TOOL_CALL_END, RUN_FINISHED.

Fails if

Any legacy type is missing — an older client would break.

S2Ordering: RUN_STARTED first, done last
curl -sN … -d '{"query":"كم عدد المحاضر؟"}' | grep -o '"type": *"[A-Za-z_]*"' | sed -n '1p;$p'

Expect

First is RUN_STARTED; last is done (kept last so existing clients still detect completion).

Fails if

done is not the final frame.

S3Repeat tool calls are distinct (the dedup bug)
اعرض المحاضر أولاً، ثم بنود الأعمال، ثم المحاضر مرة أخرى للتأكيد.

Expect

In the panel, list minutes appears as two separate chips. Each TOOL_CALL_START carries its own toolCallId.

Fails if

Only one chip appears — that is the old name-based de-duplication returning.

S4Live activity label while a tool runs
اعرض المهام المتأخرة وحللها

Expect

The thinking line reads يشغّل list tasks… while the tool runs, then returns to جارٍ التفكير….

Fails if

It always shows the generic thinking text.

S5Stop keeps the partial answer — no false error
اكتب تقريراً مفصلاً وطويلاً جداً عن جميع الاجتماعات والقرارات والمهام.

Expect

Press إيقاف mid-answer. Text already streamed stays; a quiet تم إيقاف الإجابة note appears; the composer unlocks immediately.

Fails if

It shows a red network error, wipes the partial text, or the input stays disabled.

S6Cancelling logs no stack trace
docker logs boardhub-api --since 2m 2>&1 | grep -c "Unhandled exception"

Expect

0. A client disconnect is normal and is swallowed at DEBUG, not logged as an error.

Fails if

Any count above zero — every cancellation is polluting the logs.

S7Stopping actually stops the work
docker logs -f boardhub-ai-services # watch while you press إيقاف

Expect

Model activity ceases within a second or two of Stop — the request is not left running to completion.

Fails if

Tool calls keep appearing in the log after you stopped (tokens still burning).

R

Personal reminders

A reminder is an intention about the future, private to the person who set it. These check that the assistant can set one, that the owner boundary holds, and that no caller can set one in someone else's name.

R1The assistant sets a reminder from an explicit date
ذكّرني يوم ١٠ سبتمبر الساعة ٩ صباحاً بمراجعة القرارات المتأخرة

Expect

set_reminder in the tool trace. The reply confirms the resolved date back in words, and the row appears in GET /api/reminders as PENDING.

Fails if

It says it cannot set reminders, promises one without calling the tool, or stores a different date than the one it confirmed.

R2Relative phrasing is anchored to the real meeting
ذكّرني قبل اجتماع لجنة المراجعة القادم بمراجعة عقود الموردين

Expect

list_meetings then set_reminder. The date comes from the real meeting — with AUD-2026-004 on 2 Sept the reminder lands 1 Sept 09:00 — and the row carries subjectType: MEETING and a /meetings/{id} route.

Fails if

It stores the phrase "before the next meeting" verbatim, picks a date with no meeting behind it, or leaves subjectType and route empty so the reminder cannot link back.

R3Lifecycle — create, list, delete
H=(-H "Authorization: Bearer $TOKEN" -H 'X-Tenant-Slug: acme' -H 'Content-Type: application/json') ID=$(curl -s -X POST http://localhost:8080/api/reminders "${H[@]}" \ -d '{"message":"smoke test","remindAt":"2026-09-05T09:00:00"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])') curl -s http://localhost:8080/api/reminders "${H[@]}" curl -s -o /dev/null -w '%{http_code}\n' -X DELETE "http://localhost:8080/api/reminders/$ID" "${H[@]}"

Expect

Create returns the row; the list is ordered soonest-first; delete returns 204 and the row disappears from the list (soft delete).

Fails if

The list is unordered, or a deleted reminder still appears.

R4Snooze re-arms rather than silencing
curl -s -X PATCH "http://localhost:8080/api/reminders/$ID/snooze" "${H[@]}" \ -d '{"remindAt":"2026-09-12T09:00:00"}'

Expect

snoozeCount increments and status returns to PENDING — a snoozed reminder must be picked up again, and the count is kept because repeated snoozing is itself a signal that the work is stuck.

Fails if

Status stays SNOOZED (a future delivery job would never fire it) or the count resets.

R5A reminder is private to its owner
# log in as test.member / Test@1234, then aim at a reminder owned by admin curl -s -o /dev/null -w '%{http_code}\n' -X PATCH \ "http://localhost:8080/api/reminders/$ADMIN_REMINDER_ID/snooze" "${MEMBER_H[@]}" \ -d '{"remindAt":"2026-10-01T09:00:00"}'

Expect

403. Tenant scope is not the boundary here — a reminder reveals what someone is working on, so ownership is checked on every read and write.

Fails if

200, or a 404 that leaks whether the id exists at all.

R6An ordinary user cannot set a reminder for a colleague
# as test.member (BOARD_MEMBER), aiming ownerId at the admin user curl -s -X POST http://localhost:8080/api/reminders "${MEMBER_H[@]}" \ -d '{"ownerId":"11111111-1111-1111-1111-111111111111", "message":"privilege escalation attempt","remindAt":"2026-09-07T09:00:00"}'

Expect

The ownerId is ignored: the reminder is created for test.member, source: USER, and never appears in admin's list. Nobody can plant an item in another person's day.

Fails if

It lands in admin's list — treat as a security bug, not a validation bug.

R7A privileged caller may set one for a user — write-only
# as admin (SUPER_ADMIN / SYSTEM_ADMIN / TENANT_ADMIN) curl -s -X POST http://localhost:8080/api/reminders "${H[@]}" \ -d '{"ownerId":"<test.member id>","message":"owned by the member", "remindAt":"2026-09-06T09:00:00"}'

Expect

Created with source: AGENT, visible in test.member's list and not in admin's. Admin then gets 403 trying to read or delete it — this path exists so AI Assist, which authenticates as a service account, can set a reminder that belongs to the person who asked.

Fails if

A non-admin role is allowed through, or the creator can still see the reminder afterwards.

R8Identity cannot be forged through the agent proxy
curl -s -X POST http://localhost:8080/api/ai/assist/agent "${H[@]}" -d '{ "query":"Remind me on 2026-09-10 at 09:00 to review the overdue decisions", "current_user_id":"<some other user id>"}'

Expect

The forged id is discarded — the proxy overwrites current_user_id from the JWT subject on both /agent and /agent/stream — so the reminder belongs to the caller. The same field drives the task-assignee fallback, so this covers more than reminders.

Fails if

The reminder appears in the forged user's list. Stop and treat as a security regression.

R9The 29 Aug delivery gap — now closed

Expect

Closed 30 Aug 2026. This card recorded a deliberate gap — a reminder could be set but nothing ever delivered it. Delivery, snooze-from-the-bell and a Reminders screen now exist: see sections D and X. Tick this once D1 passes.

Fails if

D1 fails — then the gap is back, and it is now a bug rather than a known limitation.

P

Minutes attribution

The transcript carries no speaker labels, yet the minutes prompt asks for an attendance section and for action-item owners. The registered attendee roster is now fetched into the context, and the rule is explicit: name a person only where the transcript says so. Added 30 August 2026

Reminders now reach the person who set them. A locked scheduled sweep turns a due reminder into a notification in the existing bell, and a Reminders screen lists what is open with snooze / done / dismiss. D

Reminder delivery

The sweep runs every five minutes on the 0 */5 * * * * cron, holds a ShedLock so only one replica delivers, and publishes into the notification pipeline that already feeds the bell. A reminder that fires must move PENDING → SENT exactly once.

D1A due reminder reaches the bell
# acme's tenant timezone is America/New_York — "due" is read on THAT clock, see D2 PAST=$(python3 -c "import datetime,zoneinfo; print((datetime.datetime.now( zoneinfo.ZoneInfo('America/New_York'))-datetime.timedelta(minutes=5)).strftime('%Y-%m-%dT%H:%M:%S'))") curl -s -X POST http://localhost:8080/api/reminders "${H[@]}" \ -d "{\"message\":\"delivery test\",\"remindAt\":\"$PAST\"}" # wait for the next 5-minute boundary, then: curl -s http://localhost:8080/api/notifications/unread-count "${H[@]}"

Expect

Within five minutes the unread count rises and a REMINDER_DUE notification appears, referenceType: REMINDER, referenceId the reminder's id, body = the reminder's own words. The reminder's status becomes SENT.

Fails if

Nothing arrives — check docker logs boardhub-api | grep "delivery sweep" first: a sweep that reports 0 delivered is a due-time problem (D2), a sweep that never logs is a scheduler problem.

D2"Due" is the tenant's clock, not the server's
docker exec -e PGPASSWORD=magales-dev boardhub-postgres \ psql -U magales -d magales -tAc "select slug, timezone from tenants" docker exec boardhub-api date # the container runs UTC

Expect

remind_at is a wall-clock value with no zone in it, so it is compared against LocalDateTime.now(tenantZone). Set a reminder for five minutes ago on the tenant's clock and it fires on the next sweep; set it five minutes ago on the server's clock and — where the two zones differ — it does not, which is correct.

Fails if

Delivery tracks the container's UTC clock. That is the bug this test exists for: a Riyadh user's 09:00 reminder arriving at 12:00 is worse than no reminder, because they stopped watching for it at 09:00.

D3A reminder fires once, not on every sweep
docker exec -e PGPASSWORD=magales-dev boardhub-postgres psql -U magales -d magales \ -c "select status, count(*) from ai_reminders group by status" # leave the stack running for 15 minutes (three sweeps), then re-count notifications docker exec -e PGPASSWORD=magales-dev boardhub-postgres psql -U magales -d magales \ -c "select reference_id, count(*) from notifications where event='REMINDER_DUE' group by reference_id having count(*) > 1"

Expect

No rows from the second query. Status moves to SENT in the same transaction that publishes, so the next sweep no longer sees it.

Fails if

Any reference_id has more than one notification — a reminder that repeats every five minutes for ever is a reason to switch the feature off.

D4Only one replica delivers
docker exec -e PGPASSWORD=magales-dev boardhub-postgres psql -U magales -d magales \ -c "select name, locked_by, locked_at, lock_until from shedlock"

Expect

One reminderDelivery row, locked_by naming the host that ran last. With docker compose up -d --scale api=2, a due reminder still produces exactly one notification.

Fails if

The table is missing (it is not a JPA entity — dev gets it from data-postgres.sql, prod from Flyway V14), or two replicas both deliver.

D5The bell entry leads somewhere

Expect

A reminder tied to a meeting deep-links to that meeting; a free-standing one opens /reminders. Neither is a dead end.

Fails if

The notification has a null route and clicking it does nothing.

D6The delivery notice is not suppressed as self-directed

Expect

The owner receives it. NotificationService.createFromEvent removes the actor from the recipients, and a reminder is the one case where actor and recipient are the same person — the job leaves actorId null on purpose. This test exists because the failure is silent: notifications simply never appear, with nothing in the log.

Fails if

The sweep logs "Delivered N" but no notification rows exist for those ids.

Z

Timezones

A reminder must arrive at the hour the person meant. Times are stored on the organisation's clock — the only reading the agent can use for "before the next meeting" — and the browser converts in both directions so the user always types and reads their own local time.

Z1What you type is what you see

Expect

On /reminders, set one for a specific local time — say 14:30 today. The row reads 14:30, in your own timezone, regardless of the organisation's. Note Arabic renders the digits as ٢:٣٠ م.

Fails if

The row shows a shifted hour. Check the org's zone against yours before assuming it is a bug — the gap will equal the offset.

Z2It fires at that local time
docker exec -e PGPASSWORD=magales-dev boardhub-postgres psql -U magales -d magales \ -tAc "select slug, timezone from tenants"

Expect

Set one two minutes ahead in your own clock; the card appears within about seven minutes (up to five for the sweep, plus the bell's poll). The stored remind_at is the organisation's wall clock, so it will read differently in SQL — that is correct, not drift.

Fails if

It arrives hours late or early. The offset between your zone and the tenant's is the size of the bug — this is exactly how the America/New_York seed was caught.

Z3No timezone preference to set

L

Cross-lingual retrieval

Arabic and English share one vector space, so one search covers the whole archive. The point of these checks is that it works in both directions — it did not before.

L1An English question finds the Arabic record
curl -s -X POST http://localhost:8081/v1/rag/search -H 'X-Tenant-Slug: acme' \ -H 'Content-Type: application/json' \ -d '{"query":"board of directors periodic meeting held in March","k":3}'

Expect

Rank 1 is the Arabic minutes of the periodic board meeting held 25 March — محضر الاجتماع الدوري الحادي عشر. The query shares no tokens with it; only the embedding connects them.

Fails if

Only English documents come back, or nothing does.

L2An Arabic question finds the English record
# ingest an English-only document first, then ask about it in Arabic curl -s -X POST http://localhost:8081/v1/rag/documents -H 'X-Tenant-Slug: acme' \ -H 'Content-Type: application/json' -d '{"documents":[{"id":"xl-probe","title":"Whistleblowing Policy", "text":"Any employee may report suspected fraud, bribery or a conflict of interest confidentially to the Audit Committee chair."}]}' curl -s -X POST http://localhost:8081/v1/rag/search -H 'X-Tenant-Slug: acme' \ -H 'Content-Type: application/json' \ -d '{"query":"كيف يبلغ الموظف عن الاحتيال أو تضارب المصالح","k":3}'

Expect

The English policy at rank 1. Delete the probe afterwards — a fabricated policy has no business sitting in a governance archive.

Fails if

Only Arabic records return. This is the direction that was broken: BM25 cannot match across languages, so before weighted fusion a cross-lingual hit was supported by one ranking while same-language hits had two, and lost on score alone.

L3Same-language retrieval did not regress

Expect

Ordinary Arabic questions still return the right Arabic records first. Weighting the semantic ranking at rag_knn_weight 1.5 must not demote exact lexical matches — BM25 is still what finds a decision number or a person's name.

Fails if

Searching a decision number stops returning that decision.

L4The agent does not search twice
هل يوجد لدينا سياسة مكتوبة بالإنجليزية عن الإبلاغ عن المخالفات؟

Expect

One search_governance call. The answer is in the user's language, and says which language the source was written in when quoting it.

Fails if

It translates the question and searches again, or says a record "may exist in the other language" — it has already searched that language.

Q

Precedent detection

Boards re-litigate settled matters because the context is gone by the time the question returns. This puts the earlier record in front of whoever is asking — as candidates, never as a verdict.

Q1Has the board decided this before?
هل سبق للمجلس أن اتخذ قراراً بشأن الميزانية التشغيلية؟

Expect

find_precedent in the tool trace. It returns decision D-2026-001 and the 25 March minutes that adopted it, each cited by number, each with what it decided and when.

Fails if

It answers from general knowledge without calling the tool, or cites nothing.

Q2Candidates, not verdicts

Expect

The wording offers related matters for the reader to judge. It must not say the matter is "already decided", "settled", or "a duplicate" — boards re-open matters deliberately, and asserting otherwise is the expensive direction to be wrong in.

Fails if

It declares equivalence, or tells the user not to proceed.

Q3Only decisions and minutes count as precedent

Expect

Library uploads and attached papers never appear as precedent. A paper someone uploaded is evidence; only a decision or the minutes record a position the board actually took.

Fails if

An uploaded document is offered as something the board decided.

Q4A miss is reported honestly
هل سبق أن قرر المجلس شيئاً بخصوص استخدام الطاقة الشمسية؟

Expect

Something equivalent to "the record does not show it" — not "the board has never discussed this". The archive's silence is not proof of absence, and in a governance tool the difference matters.

Fails if

It asserts the board never considered the subject.

T

Mid-run interrupt (browser → agent)

Until now the transport was one-way: the browser could start a run and watch it, never speak to one in flight. A picker was emitted after the run ended and clicking it began a new turn. These checks prove the answer now reaches the run that asked.

T1The run parks and says so, while still open
أنشئ قراراً جديداً بعنوان مراجعة سياسة السفر

Expect

The stream carries an AG-UI CUSTOM frame named input_required, with a runId and the board options — while the run is still open. The picker renders and the stream has not finished.

Fails if

The options only arrive with RUN_FINISHED. That is the old behaviour: the tool blocks inside agent.stream_async, so without racing the agent against an out-of-band queue the frame cannot get out and the run waits for an answer to a question nobody saw.

T2The answer reaches the waiting run
curl -s -X POST http://localhost:8080/api/ai/assist/agent/resume "${H[@]}" \ -d '{"run_id":"<runId from the CUSTOM frame>","value":"لجنة المراجعة والتدقيق"}'

Expect

{"accepted": true}, and the same SSE stream keeps producing text — it does not start over. The agent uses the chosen committee and carries on gathering the rest of the decision.

Fails if

accepted:false while the picker is on screen, or a second run appears in the transcript.

T3Clicking the picker in the browser does the same

Expect

Ask the same question in the panel and click a board. One continuous answer, no second user turn in the transcript, and the chosen board is not re-asked.

Fails if

The click posts the board name as a new message — that is the fallback path, correct only when nothing is waiting.

T4An unanswered picker does not hang the run

Expect

Ignore the picker: after 180s the run continues without a choice and says so. Close the tab instead and the parked run is released at once rather than sitting out the timeout.

Fails if

The connection is held open indefinitely, or the run errors instead of carrying on. A user who ignores a picker has not caused a failure.

T5Known limit — one replica only
Expected limit, not a bug. The parked run is a future in one process, so a resume must reach the pod holding it. With --scale ai-services=2 a resume that lands on the wrong pod returns accepted:false and the UI falls back to sending an ordinary message — degraded, not broken. Before scaling out, add sticky sessions keyed on runId or a shared channel. Tick this once you have confirmed the fallback behaves.
